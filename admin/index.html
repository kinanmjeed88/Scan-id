إعداد إصدار جديد

الحقول تجلب الحالة الحقيقية أولاً — لا تستخدم قيماً افتراضية
SemVer صارم: X.Y.Z أو X.Y.Z-prerelease؛ لا تضف +build لأن رقم البناء له حقل مستقل
عدد صحيح موجب ، يجب أن يتزايد مع نفس Core
3–5000 حرف ، لا تحتوي حقن أوامر
حسب آلية النشر الفعلية — APK + ZIP فقط
Fine-grained PAT لمستودع Scan-id فقط وبصلاحية Actions: write. يُرسل مباشرة إلى GitHub API لإطلاق سير العمل، ثم يُمسح من الحقل ولا يُحفظ في المتصفح.
لا تلصق هنا سر المستودع RELEASE_TOKEN؛ هذا السر مخصص لـ Actions. توكن اللوحة يمر مؤقتاً عبر JavaScript الصفحة، لذا استخدم توكناً محدود الصلاحية ولا تدخله إلا في النسخة الموثوقة من اللوحة.

سجل Actions (اختياري)

سير العملية المتوقع (16 خطوة)

  1. التحقق من المدخلات والصلاحيات
  2. التحقق من الفرع الهدف
  3. جلب الحالة الحالية (pubspec, Tag, Release)
  4. التحقق SemVer / Build / منع التكرار
  5. فحص التزامن (concurrency)
  6. عرض ملخص قبل التنفيذ
  7. تحديث pubspec.yaml و app_release.dart
  8. التحقق من نطاق التغيير (ملفا الإصدار فقط)
  9. تشغيل analyze & test
  10. بناء الأنظمة المختارة
  11. التحقق من APK signature و ZIP
  12. إنشاء SHA-256
  13. التحقق من عدم وجود Tag مكرر
  14. إنشاء Tag + Release + رفع الأصول
  15. التحقق من OTA (assets + digest)
  16. عرض النتيجة والروابط
أمر gh CLI (آمن — يُنفّذ محلياً بصلاحياتك)
المصادقة: التوكن المؤقت في الحقل يُرسل إلى GitHub API لإطلاق سير العمل فقط، ولا يُخزَّن بشكل دائم أو يُعرض كنص. سر المستودع RELEASE_TOKEN منفصل ويُستخدم داخل Actions لدفع ملفات الإصدار ونشره. راجع وثيقة المصادقة.

آخر 3 تشغيلات لإدارة الإصدارات

كيف تعمل؟

  • القراءة: الصفحة تستخدم GitHub API العام (api.github.com) بدون مصادقة لعرض الحالة — لا تحتاج PAT.
  • إطلاق البناء: يُرسل الزر المدخلات مباشرةً إلى workflow_dispatch على الفرع searchidf ويبقى في الصفحة؛ يلزم PAT مؤقت بصلاحية Actions: write على هذا المستودع فقط.
  • فصل الأسرار: لا يُخزَّن توكن اللوحة بشكل دائم في المتصفح، وسر المستودع RELEASE_TOKEN لا يُقرأ من الصفحة؛ يستخدمه الـ Workflow داخلياً لدفع ملفات الإصدار وإنشاء الـ Tag وRelease.
