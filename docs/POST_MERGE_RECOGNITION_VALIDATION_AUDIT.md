**Scope:** repository integrity, the recognition and intake path, existing fixtures, review/reprocessing workflow, and the validation evidence available after merge.

## Executive decision

**Historical recommendation for the audited revision: needs targeted fixes before a user-facing controlled recognition pilot.** The repository and reported CI status were healthy, and the shipped safeguards preserved source images and routed recognition through review. However, source-level control flow exposed a multi-region/all-unresolved handling gap, and the review UI had no usable “not a document” action; ordinary editor deletion of a record-linked item conflicted with the project’s record/item invariant. These were workflow correctness issues, not evidence of poor measured accuracy on real photos. Current-worktree remediation status is summarized in the addendum below.

This audit did **not** change production code. The two findings below are reproducible from the inspected branch’s conditions and invariants, but Flutter/Dart were unavailable here, so neither was executed as a runtime regression. Do not patch either path until a positive and a negative regression test are added and run. The audit makes **no claim** about Iraqi-document accuracy, and no real identity-document images or physical-device results were available.

A developer-only synthetic validation can continue. Before a user-facing pilot, close or explicitly test the two workflow findings, then run supervised Android/Windows checks with permissioned, privacy-safe representative inputs. No PR is opened solely for this audit.

### Remediation and verification status

- **F-01 — addressed in the worktree:** `RecognitionPipeline.analyze` processes measured candidates regardless of the segmenter’s `multi` hint and retains cornerless regions. The production segmenter uses the established precise whole-frame path for a resolved singleton, but keeps an unresolved singleton and all multi-region candidates; the pipeline never substitutes a full-frame result for a preserved unresolved/multi-region candidate. Source review reproduced a drop: the real segmenter returned no candidates when exactly one plausible region passed its gates, even if its corners were unresolved. It now corner-tests a lone measurement and retains it when unresolved. Stable region IDs are assigned independently of quad success. Synthetic regressions exercise the real segmenter with a singleton unresolved region, two cornerless regions, a mixed resolved/unresolved scene, plus intake-level preservation. Rejected geometry remains absent from the stored polygon; manual recovery is an axis-aligned region crop followed by a user-authored crop, not a promoted detector quad.
- **F-02 — addressed in the worktree:** the Arabic review queue now offers the explicit “ليس مستنداً” action. Dismissal is persisted as a `UserOverride.dismissed` tombstone, removes the associated layout item atomically, dissolves stale pair/group state, retains source/derived assets and evidence, survives backup/restore, is undoable, and is not re-added by reprocessing. RTL interaction, stale/repeated actions, failed-save retry, paired-record preservation and byte-preservation regressions are present. Review overrides are field-scoped: a kind correction resolves classification reasons, a pairing decision resolves pairing only, and unresolved geometry or other recognition concerns remain queued until explicitly confirmed or dismissed. Dismissing one proposed pair therefore leaves the active partner reviewable for its independent reasons; it does not dismiss or hide the partner. Ordinary final-item deletion continues to cascade its active record as in the task-start worktree; it is not being recast as dismissal. No active-record detachment field or weakened project invariant was added: no supported legacy path producing a persisted active orphan was established.
- **Manual-crop reprocessing:** the crop screen calls `ProjectService.applyManualCrop`; automatic layout remains on `applyCrop` and does not mark its result as user-authored. A caller-level audit found a subtler stale-marker path: `LocalImageEditor` preserves authorship in generic revisions, so an automatic crop could replace a manual crop yet inherit its marker. Automatic callers now explicitly clear that marker when they replace the crop; manual callers set it. `ImageAsset.userAuthoredCrop` is optional/additive, serialized only when true, defaults false for old assets, and requires a stored crop geometry. Reprocessing preserves a marked user crop and leaves the rejected detection polygon null. Regressions cover manual crop, automatic replacement through both layout and recognition, reprocess, legacy-default and backup/restore. Older manual crops lack an authorship marker, and their historical transform log is indistinguishable from automatic crops; this work does not guess which they were.
- **C — bounded large-image path:** normal direct decode remains guarded at 16 MP. JPEG sources above that limit use bounded Android sampled decoding or Windows WIC source-transform decoding, up to the existing 32 MP source and 20 MiB byte ceilings, with a working raster capped at 4 MP. Larger unsupported non-JPEG inputs fail closed with per-image errors. Tests cover planning, EXIF/coordinate mapping, small working results, corrupt/unsupported/mixed imports and original-byte preservation. The Android picker still allows up to 200 files × 20 MiB each; copies stop when the dynamic 64 MiB free-space reserve is reached. There is no separate fixed aggregate picker-byte cap (the theoretical selected-file ceiling is 4,000 MiB); that remains an explicit storage-policy risk rather than an undocumented guarantee. A Windows WIC API-signature issue found in source review was corrected; native compilation and device execution still require CI/platform validation. The pixel caps are not a measured peak-RSS guarantee. A final intake review also found that large-image import/capture surfaced sampling details while image replacement did not; replacement now reports the bounded working-copy dimensions and unchanged original alongside any aspect-ratio notice. The replacement-notice regression is included in the passing full Flutter suite. Android release and Windows release builds passed in CI, which verifies compilation but is not Android-device or Windows-installation validation.

## Recognition path and safeguards inspected

1. **Local, geometry-led detection.** `lib/imaging/document_segmenter.dart` downsizes to a working image, estimates the background from its border, applies an Otsu foreground threshold, extracts/merges connected components, then measures candidate regions before making crops. The current acceptance/rejection policy is documented in `docs/adr/ADR-012.md`: minimum component support and size/fill checks, plus typed refusals for contact with at least two frame edges, an aspect ratio above 8.0, a preview crop short side below 48 px, and regions beyond the 12-candidate cap. These are provisional geometry gates, not an identity-document classifier. No ink-density rejection rule is used (appropriately: the repository’s synthetic tests show that a solid strip and a low-contrast card need not separate on that signal).
2. **No packaged OCR engine.** The pipeline’s default is `UnavailableOcrEngine`; OCR test doubles exercise the interface, not a shipped text recognizer. Recognition must not be described as reading Arabic text or identity fields. Available signals are largely filename and shape; confidence thresholds are provisional.
3. **Abstention and layout safeguards.** `lib/domain/recognition_routing.dart` ships `AutomationMode.reviewAll`; confidence is not calibrated on a real evaluation set. An unresolved boundary does not earn a confirmed catalog size, and `lib/domain/arrangement.dart` keeps unconfirmed items off the printable sheet. The A4 layout engine remains separate from candidate detection and is not a suitable place to hide recognition errors.
4. **Originals and derived provenance.** Multi-region intake creates derived assets linked to their source; unresolved measured regions are intended to be retained as unwarped crops for manual completion. Tests assert original-byte preservation on several synthetic paths. Reprocessing keeps record/item identities and existing placement in its covered scenarios; the editor deliberately does not auto-arrange during reprocessing.
5. **Recognized candidates still need a rejection workflow.** `reviewAll` makes a wrong proposal reviewable, but review alone is not equivalent to a functional false-positive dismissal. See finding F-02.

## Prioritized findings

### F-01 — All-cornerless multi-region candidates can be skipped (P1; source-level deterministic path, not runtime-executed here)

`segmentDecoded` returns the candidate list but sets `multi` only when there are at least two candidates **and at least one has corners** (`lib/imaging/document_segmenter.dart:384-390`). If two or more measured regions have no trustworthy quadrilateral, the segmenter can therefore return `candidates.length >= 2` with `multi == false`.

`RecognitionPipeline.analyze` processes `segmentation.candidates` only inside `if (segmentation.multi)` (`lib/application/recognition_pipeline.dart:229-280`). With that valid result shape, it skips every cornerless candidate; because both local result lists remain empty, it then calls the full-frame single-image detector (`:281-310`). The resulting `ImageAnalysis` has no unresolved regions and cannot select the multi-intake path, despite the nearby comment saying full-frame fallback should happen only when nothing was measured (`:281-285`). This can turn several measured unresolved regions into a single-frame result rather than preserving each region for manual recovery. The immutable source remains recoverable, but the intended per-region workflow is not delivered.

**Coverage gap:** `test/application/recognition_pipeline_test.dart:221-264` and `test/application/smart_recognition_test.dart:251-283` test preservation by injecting `multi: true`; no inspected test drives the real segmenter’s `>=2 candidates, 0 quads` result through the pipeline. This is not a demonstrated real-photo miss; no such photo was available.

**Required verification before any code change:** add a positive regression using the real segmenter on a synthetic input that produces two or more cornerless regions, asserting both unresolved regions survive through pipeline and intake, `needsMultiIntake == true`, no guessed quad is introduced, and source bytes remain unchanged. Add negative controls for zero/no measured regions (single fallback still works), a one-region image, and a mixed resolved/unresolved multi-region image. Run them with the Flutter suite. Do not solve this by tightening unrelated thresholds or changing layout.

### F-02 — No working “not a document” action; editor deletion conflicts with record/item invariants (P1; source/invariant-confirmed, UI runtime not executed here)

The review dialog exposes confirm, type/side correction, pair accept/reject, reveal, confirm-all, and close (`lib/presentation/review_screen.dart:67-80, 141-205`); it has no dismissal action. The model already has `UserOverride.dismissed` (`lib/domain/recognition.dart:596-645`) and review routing treats it as resolved (`lib/domain/recognition_routing.dart:136-144`), but a search found no production call that writes `dismissed: true`.

The editor’s delete command calls `PageLayout.remove` (`lib/presentation/editor_controller.dart:571-579`). That method filters `items` only and preserves `documents` (`lib/domain/page_layout.dart:155-162`). For the normal recognized one-record/one-item case, deleting its item immediately violates `Project`’s `documents.length <= items.length` check (`lib/domain/project.dart:565-570`) and throws before a new project can be saved. If extra manual items happen to make the count pass, a document record can instead remain without a layout item; the model does not require every record to have a matching item. The existing delete test covers a manual, recordless item (`test/domain/page_layout_test.dart:178-192`), not this recognition-linked case. `docs/adr/ADR-012.md:124-128` says an extra accepted candidate is one the user “must delete by hand”; the inspected code does not establish that this works for its linked recognition record.

**Required verification before any code change:** add a positive editor/review regression that dismisses a false candidate and leaves no orphaned record, stale group/pair reference, or review entry; verify original and unrelated assets remain intact and undo/redo behaves. Add negative controls proving that dismissing one record does not change another record, a legitimate document, or source bytes. Reprocess the same source and confirm the explicit dismissal is not silently undone. The eventual behavior should be an explicit, undoable user decision, not a layout workaround.

### R-01 — Geometry cannot separate some artifacts from real ration-card shapes (known, explicitly bounded residual risk)

The synthetic shadow-band test documents an accepted shadow-shaped candidate at essentially the same proportion as a genuine ration-card fixture. The segmenter emits both; `reviewAll` routes both for a user decision. This is not a newly discovered defect and does not justify tightening the aspect threshold or adding an ink-density rule: the paired tests show such a threshold can refuse a genuine card first. Until a real labelled set supports a different signal, keep this ambiguity visible and reviewed.

### R-02 — Touching documents and complex backgrounds can defeat segmentation (known trade-off)

The synthetic touching-pair test establishes a case where two touching narrow shapes merge, the merged region is rejected, and a visible gap yields three document records/items. The original is kept and the refusal is reportable, but this is not equivalent to successful multi-document recognition. The documentation also states the near-uniform-background limitation. Include these cases in any supervised evaluation; do not alter the A4 layout engine to compensate.

### E-01 — Real-photo and device evidence is absent

There is no permitted representative photo set in the checkout and no physical Android/Windows runtime was available. CI builds and synthetic pixel fixtures cannot establish crop quality under camera perspective, glare, blur, shadows, handling, compression, or varied backgrounds; nor can they establish Iraqi-document category accuracy. The app currently has no packaged OCR engine. This is an evidence limitation, not a basis for inventing results.

## Remediation and controlled-validation plan

1. **Close F-01 with real-pipeline regression tests.** Test all-unresolved, mixed, and single/no-region cases at the segmenter → pipeline → intake boundary. Assert candidate counts, review routing, no fabricated corners, crop usability, stable IDs, and original-byte preservation.
2. **Close F-02 with an explicit dismissal workflow.** Define whether dismissal removes the item, retains a dismissed record for provenance, or both; keep the project invariants, layout groups, pair links, review queue, and undo/redo consistent. Test reprocessing and unrelated-document preservation. Do not rely on ordinary delete until its behavior is proven.
3. **Then run a permissioned, privacy-safe evaluation set locally.** Use synthetic or owner-approved/redacted inputs and keep personal identity images out of Git, public services, and external APIs. Include zero/one/multiple documents; each intended category; landscape/portrait/rotated captures; easy and hard boundaries; blank paper and other non-document shapes; touching/separated cards; and simple/complex backgrounds. Record case ground truth and expected regions before inspecting outputs.
4. **Report outcomes per case and then by a predeclared aggregate protocol.** Separate true detected regions, misses, false candidate regions, explicit rejected regions (with reason), review-routed unresolved candidates, and confirmed/rejected user decisions. For each crop, record whether it is usable, whether orientation is correct, whether a perspective boundary was trustworthy, and whether reprocessing preserves IDs, geometry, decisions, and originals. Calculate precision/recall only over a labelled set with unambiguous ground truth; never equate “reviewed” with “correct.”
5. **Perform actual platform checks.** On an Android device and a Windows installation, verify import, progress/cancel, review correction/dismissal, manual crop recovery, reprocessing, export, backup/reopen, and OS share handoff. Record device/OS/build versions and failures. CI’s callback/build checks are not substitutes for these runs.
6. **Re-run CI after any source fix.** Require formatting, analyzer, all Flutter tests, independent PDF/raster export audit, and Android/Windows release builds. Keep synthetic evidence and real-photo/device evidence in separate result columns.

No OCR/network feature, threshold adjustment, universal ink rule, preset-dimension change, or A4-layout change is recommended by this audit. No production changes, commit, PR, or merge were made.

## Final assessment

Repository integrity and the reported CI checks are good; synthetic tests provide meaningful coverage of segmentation gates, source preservation, provenance, review routing, reprocessing, and export workflow. They also expose an acknowledged geometry-only false-positive risk and a touching-document trade-off. The current evidence is **not sufficient for an Iraqi-document accuracy claim or an unsupervised release**. Because F-01 and F-02 are specific, testable workflow gaps, the disposition is **needs targeted fixes before a user-facing controlled pilot**, followed by privacy-safe representative and physical-device validation.
