# ADR-005 — Offline-first recognition

- **Status:** Accepted
- **Date:** 2026-10-08

## Context
Scan-id is an offline workspace. The release Android manifest declares **no
INTERNET permission** (`android/app/src/main/AndroidManifest.xml`; only
`debug`/`profile` add it per the Flutter template), `allowBackup=false`, and
data-extraction rules are set. `lib/` imports no networking package
(`package:http`, `HttpClient`, `dio` are absent); `dart:io` is used only for
file IO.

## Decision
Recognition is fully offline. **No** cloud document upload, **no** remote OCR,
**no** runtime model download. Models are bundled with the app, listed in a
manifest with hashes and licenses, and never fetched at runtime.

## Consequences
- A CI **import guard** must fail the build if recognition code imports a
  networking library.
- Model candidates must run on-device on Android and Windows, CPU-capable, with
  offline packaging (see the OCR/Model Evaluation Plan in `docs/AUDIT.md`).
- Privacy invariants (no INTERNET, no telemetry of document contents) are
  unchanged and re-audited each phase.

## Alternatives considered
- Cloud OCR/inference — rejected: violates the offline mission and privacy
  requirements; would require adding INTERNET, which is prohibited.

## Amendment — 2026-10-16: the one socket this app is allowed to open

The context above said the release manifest declares **no INTERNET**, and that
`dart:io` is used only for file IO. Both were true when written, and both were
the reason the in-app update check could never work on a user's phone: the
Android release build cannot open a socket without `INTERNET`, so every check
failed in the kernel before the code saw an answer — while the screen told the
person to check their connection.

This decision is not reversed. **Recognition, correction, storage, backup and
export remain fully offline, and no document data may ever reach the network.**
What is added is one narrow, user-initiated exception, so that the app can
finish the job it already promised to do.

### What is now permitted

- The `INTERNET` and `REQUEST_INSTALL_PACKAGES` permissions in the release
  manifest — that exact pair, asserted by `tool/check_source.py`, so a widened
  grant fails the gate the same way a missing one would.
- Reading published release metadata over HTTPS from the fixed hosts listed in
  `_trustedUpdateHosts` (`lib/application/ota_update.dart`), redirects refused,
  size bounded, with a connect/read timeout so a captive portal cannot hang the
  settings screen.
- Downloading the release asset into `cache/scan-updates` (the app's own
  directory), verifying it against the published SHA-256, and — before the
  installer is offered anything — comparing the package's signer with the
  certificate of the app installed on this device and with
  `EXPECTED_UPDATE_CERT_SHA256`, the fingerprint compiled into this build from
  the release configuration. An unsigned package, a package with more than one
  signer, or a package whose `applicationId` is not this app's is refused; so is
  one whose identity cannot be established, because an update path is exactly
  where "could not verify" must not be treated as "fine". A rotated certificate
  is honoured only when the platform's own signing-certificate history names the
  installed one, never because a release note said so.
- Asking the release feed one question, in one way: an HTTPS GET of a fixed
  path, carrying the standard `Accept`, `User-Agent` and
  `X-GitHub-Api-Version` headers. No version number, no name, no project and no
  identifier is sent, at any point. What the feed can observe is an address and
  a time, as with any HTTPS request.

### Where a publisher identity comes from

A release cannot vouch for itself. The notes, the asset list and the
`SHA256SUMS` file are produced by the same account that publishes the APK, so an
attacker who reaches the release reaches the digest too, and a matching digest
is then proof of nothing but arrival. Verification therefore rests on values the
release does not control:

1. **The device.** `UpdateInstaller.kt` reads the certificate of the app
   already installed (`getPackageInfo(..., GET_SIGNATURES)`) and requires the
   downloaded package to carry that same signer. This is the primary anchor: it
   is local, it is what Android itself refuses to override, and it works even if
   the pin below were missing.
2. **The build.** `EXPECTED_CERT_SHA256`, declared once per release workflow,
   is compared by CI against the keystore and against the built APK, and is
   compiled into that APK as `BuildConfig.EXPECTED_UPDATE_CERT_SHA256`. It is a
   public certificate fingerprint, not a secret, and it changes only by pull
   request. It decides when the installed package cannot be read, and it is
   what makes a build without a matching keystore unusable as an update.
3. **The rotation record.** A new signing certificate is accepted only when the
   platform's own `signingCertificateHistory` names the certificate this
   installed app carries — never because a release said the key changed.

The value pinned today is the fingerprint of the release certificate generated
on 2026-10-15, recorded with its verification evidence in
`docs/FINAL_AUDIT_2026-10-16_FOLLOWUP.md`; it was read from CI, not derived from
this app's own release metadata.

Windows has no such anchor yet: no Authenticode certificate, no signing step and
nothing in this repository verifies a `.zip`, so the Windows build keeps the
downloaded-and-verified package and refuses to run it. That asymmetry is the
honest state, and closing it needs a publisher-supplied signing certificate —
not a workaround in code.

### What stays forbidden

Uploading images, project data, names, or telemetry; fetching a model at
runtime; cloud OCR or inference; an installer path on a platform where the
package is not signed and verified first (`UpdateService.installUpdate` refuses
instead of guessing). A build with no installer configured says so, in words the
tests assert.

### Consequences

- `docs/ARCHITECTURE.md` (S8) and `docs/AUDIT.md` describe the lifecycle and the
  permission gate; the CI privacy gate reads "exactly these two permissions"
  rather than "no INTERNET".
- The privacy sentence users can see, in the update card itself, states that
  networking is used for this check and this download only.
- The refusal is not prose in a document: `tool/check_source.py` fails when the
  Kotlin comparison loses an anchor or starts the installer before the check
  returns, and the Dart tests fail when a refused handoff is reported as
  success.

## Amendment — 2026-10-17: the same question, asked when the app opens

The 2026-10-16 amendment described one user-initiated check, reachable from
Settings. That left the update invisible to anyone who never opened Settings
and pressed «التحقق من التحديث», so a superseded build could keep running for
the life of its installation. The check now also runs once, at launch.

Nothing else about the permission changes:

- The request is the same one: a fixed HTTPS path, the same three headers, no
  version, name, project, image or identifier of any kind. The feed still sees
  only an address and a time.
- The launch check is silent: an unreachable feed, a captive portal, a timeout
  or an answer of «nothing newer» is not reported. Only a published newer
  release speaks, and only to state its version and ask.
- It downloads nothing. The download still starts only when the person accepts
  the offer, and a package is handed to the installer only after the digest and
  signer checks above.
- An answer that arrives after the person has opened a project or Settings is
  dropped rather than covering that work; Settings keeps its on-demand check.

`README.md` and the About dialog were updated in the same change, because both
stated that the network was opened only on request.
