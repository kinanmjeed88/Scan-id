# ADR-008 — Multi-document recognition entity chain

- **Status:** Accepted
- **Date:** 2026-10-08

## Context
One source image may contain zero, one or many documents, and a logical
document may have a front and a back side. The current model is effectively one
`ImageAsset` → one `DocumentItem`. The specification defines an explicit chain.

## Decision
Adopt the recognition entity chain where appropriate:

```
SourceImage → DetectedDocument → DocumentInstance → DocumentSide
            → ProcessedDocumentAsset → DocumentLayoutItem
```

Mapped onto existing Scan-id concepts (no duplication):

| Spec concept | Current | Action |
|---|---|---|
| SourceImage | `ImageAsset` (immutable original) | reuse |
| DetectedDocument | — | new (id, polygon, bbox, `detectionConfidence`, quality/visibility, producer+version) |
| DocumentInstance | — | new (one logical doc, 1–2 sides, pairing state) |
| DocumentSide | — | new (front/back/unknown) |
| ProcessedDocumentAsset | derived `working` under `edits/<id>` | extend to a first-class, per-detection derived asset (corners, transform, output size, effective DPI, version) |
| DocumentLayoutItem | `DocumentItem` | reuse/extend (add preset snapshot, provenance, override refs, group id) |

## Consequences
- Multiple detections per source become multiple derived assets and layout
  items, all tracing to one immutable `SourceImage`.
- Front/back pairing produces `UncertainPairing` for review rather than two
  unrelated documents.
- Provenance on every derived object answers "where did this come from?" and
  "why was it classified this way?" without storing OCR text.

## Alternatives considered
- Keep one-image-one-item — rejected: cannot represent multi-document photos or
  front/back pairs, which are core to the mission.
