# ADR-010 — Explicit schema migration before recognition metadata is persisted

- **Status:** Accepted
- **Date:** 2026-10-08

## Context
Today, opening older projects works through implicit, forward-compatible
parsing in `Project.fromJson` (accepts `schemaVersion` 1–4, with defaults such
as `sizeConfirmed=false` forcing legacy items off-sheet). This is fine for
additive, backward-compatible reads, but it is **not** an explicit, auditable,
idempotent migration with snapshot/rollback — which the specification requires
before new recognition/provenance/override/preset-snapshot/group state is
persisted.

## Decision
Before any recognition metadata becomes persisted, introduce an **explicit**
migration step for the project record. Migration must be:
- **deterministic** (same input → same output, no timestamps/randomness in the
  transform),
- **idempotent** (running it twice changes nothing the second time),
- **non-destructive** (opening a legacy project never mutates it; the upgrade
  happens only on explicit save/upgrade, after an automatic pre-upgrade
  snapshot),
- **failure-safe** (atomic write: temp → verify → replace; a future/unsupported
  schema fails with a clear message; a malformed one fails with a typed error; a
  fault mid-migration leaves the original intact).

## Consequences
- The migration matrix (v1, v2, v3a, v3b, v3c, v4 → v5, plus v5→v5 unchanged,
  malformed, unsupported-future, and interrupted-with-rollback) becomes a
  required, tested contract.
- Backups (`.scanid`) and restore must round-trip the new state and exclude
  models and OCR text.
- No migration code is written in Phase 0; this ADR governs Phase 1 (Gate 1).

## Alternatives considered
- Continue implicit `fromJson` parsing only — rejected: cannot guarantee
  idempotency, snapshot/rollback, or safe rejection of future schemas under
  fault injection.
