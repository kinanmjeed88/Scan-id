# ADR-011 — Persistence schema version becomes 5

- **Status:** Accepted (decision only). Implementation is deferred to Phase 1
  and gated by Gate 1. No migration code is written in Phase 0.
- **Date:** 2026-10-08

## Context / ambiguity being resolved
The current repository fact is `Project.schemaVersion = 4`
(`lib/domain/project.dart`), and `Project.fromJson` accepts `{1, 2, 3, 4}`.
PR #5's title ("Document Schema v5 migration and smart layout architecture")
used "v5" in an **architectural / data-model** sense (the smart-layout model:
`DocumentSizeCatalog`, `document_kind`, `arrangement`, `packing`), while the
on-disk integer remained `4`. This ADR decides whether the Smart Recognition
persistence model should make `schemaVersion` literally `5`, or keep "v5" as a
label only.

## Decision
**Adopt `schemaVersion = 5`** for the Smart Recognition persistence model. "v5"
becomes both the architectural label and a concrete on-disk version.

Rationale: Phase 1+ will persist genuinely new, additive state on the project
record — recognition metadata and versions, the provenance chain, preset
variants and per-item preset snapshots, the user-override layer, front/back
instance/side references, and layout-group ids. A new persisted shape must be
version-gated so that (a) migration is explicit and testable (ADR-010), and
(b) older app versions safely **reject** a v5 record instead of misreading it —
exactly the guarantee schema 4 already provides for older readers.

## Purpose of schemaVersion 5
Version-gate the recognition-aware project record: detection/instance/side
references, processed-asset references, recognition results with versions and
the five confidence dimensions, preset variant + snapshot, user-override layer,
and keep-together layout-group membership — all additive with safe defaults for
records that predate them.

## Migration boundary
- **Read:** v5 must open v1, v2, v3a, v3b, v3c and v4 (chaining through the
  existing forward-compatible parsing, then applying the explicit v5 upgrade).
- **Write:** new/upgraded projects are written as v5.
- **v4 → v5** is additive with defaults (existing `documentKind`,
  `recognitionConfidence`, `sizeConfirmed`, layout, crop, lock state are
  preserved; new recognition fields default to "absent/unrecognized").
- **Backward compatibility:** an app older than v5 must reject a v5 record with
  a clear message and must never silently downgrade or misread it (symmetric
  with today's schema-4 behavior, already covered by `legacy_schema_test.dart`).

## Snapshot / rollback
- An automatic **pre-upgrade snapshot** is taken before any v4→v5 upgrade.
- Writes are **atomic** (temp → verify → replace); a fault mid-migration leaves
  the original intact and the snapshot restorable.
- Migration is **deterministic, idempotent, non-destructive and failure-safe**
  (ADR-010).

## What is explicitly NOT decided here
- The exact JSON field layout (Phase 1 design, Gate 1).
- Whether recognition metadata lives inline on `DocumentItem` or in a parallel
  record keyed by id (Phase 1 design decision; ADR-004 requires the override
  layer be separate regardless).

## Consequences
- `Project.schemaVersion` becomes `5`; `fromJson` accepts `{1,2,3,4,5}`;
  `legacy_schema_test.dart` gains v4→v5 and the full matrix.
- No behavior change to existing v1–v4 reads in Phase 0; the bump and migration
  land together in Phase 1 behind Gate 1.

## Alternatives considered
- Keep `schemaVersion = 4` and treat "v5" as a label only — rejected: new
  persisted state would be smuggled into a v4 record with no version gate,
  breaking the safe-reject guarantee and the explicit-migration contract.
- Jump to a higher version — rejected: `5` is the next integer and matches the
  established sequence.
