# ADR-013 — Deleting an image is one planned operation that unlinks what depends on it

- **Status:** Accepted
- **Date:** 2026-10-11

## Context

The image-management screen offered «إزالة من قائمة الصور». It called
`ProjectService.removeAsset`, which refused whenever the image was still
referenced: by an A4 element, by a recognition record, or by a processed file
inside the image's folder. The refusal told the user to remove the elements
first, which sent them to the sheet editor. A dismissed recognition region also
protected its image forever, so the only way out was to edit the sheet by hand.

The guard was not wrong about the danger. Deleting an image while elements still
point at it would leave a broken project. The defect was that the app asked the
user to perform the unlinking, which the app itself knows how to do.

## Decision

1. **One pure plan** (`lib/domain/image_deletion.dart`). `planImageDeletion`
   computes, from the project alone, every element, record and derived image the
   deletion touches. The confirmation text and the applied change come from the
   same plan.
2. **Ownership, not similarity.** An element or record belongs to an image when
   it names the image as its source or lives in the image's own folder. Matching
   by dimensions, names or pixels is never used.
3. **Unlinking uses the editor's own rule.** Sheet elements leave through
   `PageLayout.remove`, which cascades to records and pair links. The new
   `allowLocked` parameter is set only by these deliberate removals; the editor's
   default still refuses locked elements.
4. **Derived images stay.** A crop made from the image is an independent picture
   that may be in use. It remains in the project with its files. Its `derivedFrom`
   is kept, so it is never reclassified as an original photo, which would make it
   eligible for reprocessing. The existing provenance report already lists such
   chains as broken, and the confirmation says so.
5. **Order of writes.** Metadata is saved first, in one revision-guarded save.
   Only after that succeeds is the image's folder removed. A failed save leaves
   every file in place. A failed folder removal returns a warning; the image is
   already gone from the project and its folder is unreferenced, so the storage
   maintenance screen can remove it later. Nothing points at it.
   - **Recovery copies count as references.** The recovery copy of a project is
     written after the metadata commit. If that write fails, the copy still
     names the image's folder. `LocalStorageMaintenance.deleteFiles` and
     `deleteProjectFiles` therefore refuse any path a live recovery copy or a
     pre-upgrade snapshot names. The folder is kept and reported as a warning.
     Without this guard, a later recovery would restore a project whose files
     were already gone.
   - **Maintenance classifies, it does not guess.** Each unreferenced folder is
     either *unused* (removable after the grace window), *retained* (named only
     by a recovery copy or snapshot, kept until that copy is rewritten), or *live*
     (named by a saved project, never listed). `OrphanFiles.retained` reports the
     middle group.
   - **Staleness is per project and durable.** A project is stale when its copy
     is missing, unreadable, marked deleted, or at a different revision from the
     saved record. This is computed from the copies, so it survives a restart.
     Saving another project does not clear it. `refreshRecoveryPoint` rewrites
     one copy and fails if it still cannot be written. A project that exists
     only in the copies is never tombstoned automatically: an empty database
     after corruption must not erase recovery data.
   - **Save order.** The database commit comes first. A failed copy write does
     not fail the save, because the data is already committed; the project is
     reported as stale instead. **Removal order is the reverse:** the tombstone
     is written first and must succeed, then the record is deleted. If the
     record delete fails, the live copy is written back.
6. **Backups, checkpoints and shared files are never deleted by this operation.**
7. **Removing from the sheet is a separate action** (`removeImageFromSheet`). It
   keeps the image and its files.

## Consequences

- Full deletion needs no detour through the sheet editor, and no unlock step.
- A dismissed region on the deleted image is removed with it and counted in the
  confirmation. Nothing keeps that decision after the deletion. Re-importing
  the same file later shows its regions for review again. Reprocessing cannot
  run on a deleted source. A derived crop whose source was deleted keeps its
  files, elements and `derivedFrom`, is reported as a broken chain, and is never
  reprocessed as a photograph (`test/application/reprocess_test.dart`).
- `ProjectService.removeAsset` is removed. Callers use `deleteImage` or
  `removeImageFromSheet`.
- Tests: `test/application/image_deletion_test.dart` covers the sixteen storage
  scenarios on real sembast storage and real files, plus the recovery-copy
  partial failure and the maintenance classes; `test/domain/image_deletion_test.dart`
  covers the pure plan. The widget test in `test/widget_test.dart` drives the
  image menu and confirmation end to end.
